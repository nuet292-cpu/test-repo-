## 1. Project Overview

### 1.1 Brand name

**Bandly** — *"Speak. Score. Improve."*

- Short (6 letters), easy to say and type, and it means one thing: getting your IELTS **band**.
- Domain at launch: `bandly.vercel.app` (free). Later, if available: `bandly.app` or `getbandly.com`.
- Backups if the name is taken: **Spekko**, **Bandup**, **Oralo**.
- Before committing, check that the name is free on GitHub, Vercel, and a quick trademark/domain search.

### 1.2 What the app does

Bandly is a web app where students practise the **IELTS Speaking test** with an AI examiner that behaves like a real one:

- The student picks **Part 1**, **Part 2**, **Part 3**, or the **Full Test** (all three parts, about 11–14 minutes).
- The AI examiner welcomes the student, introduces itself, explains the format of what was chosen, explains each part's rules, asks questions from the database, keeps time, and formally closes the test.
- The student answers by voice. Answers are transcribed and assessed against the four official IELTS criteria.
- After the test the student gets an **estimated band score** (overall + per criterion), detailed feedback, and concrete suggestions for improvement.
- All results and transcripts are saved to the student's history so they can track progress.

**MVP scope (v1):** Speaking module only.
**Later (v2+):** IELTS resources library, band score calculator (Listening/Reading raw-score → band, overall band), more modules.

### 1.3 Roles and dashboards

| Role | Who | Can do | Area |
|---|---|---|---|
| **Guest** | Anyone, not signed in | Browse landing page, how it works, test format guide, sample questions | `/` public pages |
| **Student** | Signed-in user (default role) | Take tests, see results, history, progress, settings, delete account | `/app/*` |
| **Admin** | Content manager | Everything a student can + manage question bank, topics, cue cards, examiner scripts, audio, CSV import | `/admin/*` |
| **Superadmin** | You (the owner) | Everything an admin can + manage users and roles, usage and quota dashboard, app settings (daily limits, AI models, maintenance mode), audit log, retry failed evaluations | `/admin/*` + `/admin/system/*` |

- Roles are stored in Clerk `publicMetadata.role` (`student` | `admin` | `superadmin`) and mirrored in the database.
- The first superadmin is set from an env variable (`SUPERADMIN_EMAILS`) so you never lock yourself out.
- Only a superadmin can promote or demote admins.

### 1.4 The examiner's behaviour (the core of the product)

The examiner must sound like a real IELTS examiner: **formal, polite, calm, clear, encouraging but neutral**. No jokes, no slang, no "Great answer!", no small talk beyond what the real test does. It never gives feedback during the test.

**Key design decision:** every examiner line except the questions is **scripted text, not generated by the LLM**. This makes the examiner consistent, exam-like, fast, and free (the audio can be generated once and reused). The LLM is used for **assessment**, where its intelligence actually matters.

Example script (stored in the database, editable by admins):

| Moment | Examiner says |
|---|---|
| Welcome | "Good morning. Welcome to your IELTS Speaking practice test. My name is Sarah Collins, and I will be your examiner today. This test is recorded for assessment purposes." |
| Identity | "Could you tell me your full name, please?" … "Thank you." |
| Format (Full Test) | "The Speaking test has three parts and takes between eleven and fourteen minutes. In Part 1, I will ask you some questions about yourself and familiar topics. In Part 2, you will speak about a topic for one to two minutes. In Part 3, we will discuss some more general questions related to the Part 2 topic. Please answer as fully and naturally as you can." |
| Format (single part) | Only the chosen part is described, e.g. "Today you will practise Part 2 of the Speaking test only…" |
| Part 1 intro | "Let's begin Part 1. In this part, I'd like to ask you some questions about yourself." |
| Part 1 topic change | "Now, let's talk about *{topic}*." |
| Part 2 intro | "Now, I'm going to give you a topic, and I'd like you to talk about it for one to two minutes. Before you talk, you will have one minute to think about what you are going to say. You can make some notes if you wish. Here is your topic." |
| Part 2 start | "All right. Remember, you have one to two minutes for this. I'll tell you when the time is up. Please start speaking now." |
| Part 2 time up | "Thank you." + one rounding-off question |
| Part 3 intro | "We've been talking about *{topic}*, and I'd like to discuss with you one or two more general questions related to this." |
| Ending | "Thank you. That is the end of the Speaking test. Your responses will now be assessed, and your estimated band score with detailed feedback will be ready in a moment." |

Fixed examiner identity (one name, one voice) for the whole app — consistency feels professional.

### 1.5 Important honesty notes for students

- Scores are **estimates**, not official IELTS results. Show this clearly on every results page.
- **Pronunciation** can only be estimated from transcription confidence, speech rate, and pauses — it is the least reliable criterion. Label it "estimated (limited)".

### 1.6 Question content note

Cambridge IELTS books are copyrighted. For a public app, prefer questions you write yourself, paraphrased common topics, or sources that explicitly allow reuse. Store a `source` field on every question so you can audit content later.

## 3. Application Workflow

### 3.1 End-to-end pipeline

```
Student signs in (Clerk)
      │
      ▼
Chooses mode: Part 1 | Part 2 | Part 3 | Full Test
      │
      ▼
Mic check page (permission + level meter + 5-sec test recording)
      │
      ▼
POST /api/sessions  → server picks questions from DB, snapshots them into test_sessions
      │
      ▼
Exam Room (client state machine)
  ├─ Examiner plays scripted audio (cached TTS)  ──► captions optional
  ├─ Examiner asks question (cached question audio)
  ├─ Recording starts automatically (beep + red indicator + timer)
  ├─ Student answers → stops by "Finish answer", silence, or time limit
  ├─ Audio blob → POST /api/stt → Groq Whisper → transcript saved in `responses`
  │     (runs in background while the next question plays)
  └─ Repeat until part/test ends → examiner closing script
      │
      ▼
POST /api/sessions/:id/evaluate  → status = "evaluating"
  ├─ Gather transcripts + speech metrics (wpm, pauses, confidence)
  ├─ LLM call with versioned prompt + band descriptors → strict JSON
  ├─ Validate JSON with zod → compute overall band (official rounding)
  └─ Save to `evaluations`, status = "evaluated"
      │
      ▼
Results page: overall band, 4 criteria, feedback, suggestions, transcript review
      │
      ▼
History & progress dashboard
```

### 3.2 Question selection rules

| Part | Selection |
|---|---|
| Part 1 | 1 "about you" topic (work/study/hometown/home) + 2 other familiar topics, ~3–4 questions each (~10–12 total) |
| Part 2 | 1 cue card (topic + 3–4 bullet points + "and explain…") + 1 rounding-off question |
| Part 3 | 4–6 discussion questions **linked to the Part 2 cue card's theme** (like the real test) |

- Only `published` questions are used.
- Avoid repeats: exclude questions the student saw in their last N sessions (fallback to repeats if the bank is small).
- Question selection happens **on the server**, and the chosen set is saved as a snapshot in the session. If an admin edits a question later, old results still show what was actually asked.

### 3.3 Exam timing (enforced by the client, recorded by the server)

| Item | Limit | What happens at the limit |
|---|---|---|
| Part 1 answer | soft 30s, hard 60s | Recording stops, examiner moves on |
| Part 2 preparation | exactly 60s with notes box | Examiner says "start speaking now" |
| Part 2 long turn | min suggestion 60s, hard 120s | Examiner: "Thank you." |
| Part 3 answer | hard 90s | Recording stops, next question |
| Silence auto-stop | ~4s silence after speaking started (stage 9 enhancement) | Answer ends |

### 3.4 Voice interaction design (how the examiner talks)

- **One voice, one name** for the examiner across the entire app.
- **All fixed lines are pre-generated once** (admin clicks "Generate audio") and stored in Vercel Blob. Question audio is generated when an admin publishes a question. At test time the app only *plays files* — no TTS API calls, no delay, no rate-limit risk.
- **Preloading:** while the student answers question *n*, the audio for question *n+1* is already downloading.
- **Turn-taking:** examiner audio ends → short pause (~400ms) → soft beep → recording indicator. The student never has to guess when to speak.
- **Captions:** "Practice mode" shows examiner captions; "Exam mode" hides them (like the real test). Part 2 cue card is always shown on screen (as in the real exam).
- **Fallback:** if a cached audio file is missing or fails to load, use the browser's `speechSynthesis` with the same text. If that is unavailable too, show the text with a "Read the question" note. The test never blocks on audio.
- **Interrupting:** the examiner never cuts in mid-sentence by AI decision; only time limits end answers, which matches real exam behaviour.

### 3.5 Prompt management

- All prompts live in code: `src/lib/ai/prompts/` — e.g. `evaluate-speaking.v1.ts`. Never inline prompts inside route handlers.
- Each prompt file exports: `version`, `system` text, a `buildUserMessage()` function, and the zod output schema.
- Band descriptors (paraphrased from the public IELTS Speaking band descriptors) live in `src/lib/ai/band-descriptors.ts`, shared by all prompts.
- Every saved evaluation stores `model` and `prompt_version`, so old and new results are comparable and regressions are traceable.
- Changing a prompt = new version file + rerun the golden test set (see 3.6) before merging.

### 3.6 Assessment consistency

| Technique | Detail |
|---|---|
| Deterministic settings | `temperature: 0` (or ≤0.2), fixed `seed` where supported |
| Structured output | JSON mode / `response_format` + zod validation; on invalid JSON → retry once with a "fix the JSON" instruction |
| Rubric-first prompt | The model must quote evidence from the transcript for each criterion **before** giving a score |
| Code does the math | LLM gives 4 criterion bands (0–9, whole numbers). **Code** computes overall: average rounded to nearest 0.5 using IELTS rounding (x.25 → x.5, x.75 → next whole) |
| Objective metrics as input | Words per minute, number/length of pauses (Whisper segment timestamps), filler-word count, average transcription confidence, answer length. Passed to the LLM as facts |
| Calibration examples | 2–3 short anchor transcripts with known bands (≈5.0, 6.5, 8.0) in the prompt |
| Guardrails | Very short answers (<10 words) or empty transcripts cap scores; off-topic answers flagged |
| Golden test set | ~15 transcripts with expected bands stored in `tests/fixtures/golden/`. A script runs them against the real model; pass = each criterion within ±0.5 of expected, ≥ 80% match |

**Evaluation output schema (simplified):**

```ts
{
  criteria: {
    fluencyCoherence:  { band: number, evidence: string[], strengths: string[], improvements: string[] },
    lexicalResource:   { ... },
    grammaticalRange:  { ... },
    pronunciation:     { ... , limited: true }
  },
  partFeedback: { part1?: string, part2?: string, part3?: string },
  betterAnswerExamples: { question: string, original: string, improved: string }[], // 2–3 items
  topSuggestions: string[]   // 3–5 actionable steps
}
```

### 3.7 API errors and rate limits

All AI calls go through one module: `src/lib/ai/client.ts`. Nothing else calls Groq directly.

| Problem | Handling |
|---|---|
| Timeout | 30s timeout per call (AbortController) |
| 429 rate limit | Read `retry-after` header → wait and retry (max 2 retries, exponential backoff + jitter). If still limited → try next model in fallback chain |
| 5xx | Retry with backoff, then fallback model |
| Invalid JSON | One repair retry, then mark evaluation `failed` |
| STT failure for one answer | Save response with `transcript_status = failed`; the test continues; a "Retry transcription" is attempted at evaluation time (audio kept temporarily in memory/IndexedDB on client until the session finishes) |
| Daily quota exhausted | Session is saved with status `pending_evaluation`; student sees "Your test is saved. Your score will be ready soon." with a "Check again" button; superadmin can bulk-retry from dashboard |
| Abuse prevention | Upstash rate limits: per-user (e.g. 3 full tests/day, configurable by superadmin), per-IP on public endpoints, global daily budget guard tracked in `api_usage` table |

User-facing error messages are calm and specific: *"We couldn't hear that answer clearly. Let's continue — this won't stop your test."* Never show raw error text.

## 4. User Experience and UI/UX

### 4.1 Design direction

- **Feel:** calm, trustworthy, academic-but-modern. Think "premium exam prep", not "AI toy".
- **Colour palette:**
  - Primary: deep indigo/navy (`#1E2A5A`-ish) — trust, exam seriousness
  - Accent: warm amber (`#F2A93B`-ish) — progress, scores, highlights
  - Neutrals: slate greys; success green, warning amber, error red (all WCAG AA contrast-checked)
  - Light and dark mode via CSS variables (shadcn theme tokens)
- **Typography:** Plus Jakarta Sans for headings, Inter for body; type scale 14/16/18/24/32/48; body line-height 1.6.
- **Spacing:** 4px base grid (Tailwind default), consistent section padding, max content width ~1200px.
- **Rules to avoid the "AI-generated look":** no purple-gradient everything, no emoji headings, no random glassmorphism, consistent radius (one value, e.g. 12px), real copy (no lorem ipsum), real screenshots of the exam room on the landing page.

### 4.2 Aceternity-inspired, not copied

Use 2–3 lightweight effects **only on the landing page**, rebuilt simply with Tailwind + Motion:
- Subtle grid/dot background with a spotlight in the hero
- Animated band-score card in the hero (number counting up)
- Hover lift on feature cards

The exam room and dashboards stay calm and distraction-free (no moving backgrounds).

### 4.3 Key screens

| Screen | Notes |
|---|---|
| Landing (`/`) | Hero, how it works (3 steps), test format explainer, sample result preview, FAQ, CTA |
| Sign in / up | Clerk hosted components styled to match theme |
| Student home (`/app`) | "Start a test" cards (Part 1/2/3/Full), last score, streak, recent results |
| Test setup (`/app/test/new`) | Mode, practice vs exam mode, mic check |
| Exam room (`/app/test/[id]`) | Examiner card (name, subtle voice waveform when speaking), current part + progress, timer, recording indicator, Part 2 cue card + notes pad, "Finish answer" button, "End test" (with confirm dialog) |
| Evaluating (`/app/results/[id]`) | Step loader: "Transcribing… Assessing fluency… Preparing feedback…" |
| Results | Overall band (large), 4 criteria cards, radar chart, strengths/improvements, improved-answer examples, full transcript with per-question view, disclaimer |
| History (`/app/history`) | Paginated list + filters + progress line chart |
| Settings | Profile, target band, exam mode default, delete my data |
| Admin (`/admin`) | Overview stats, Questions (table + filters + create/edit drawer), Topics, Cue cards with linked Part 3, Examiner scripts (edit + regenerate audio + preview), CSV import with validation preview |
| Superadmin (`/admin/system`) | Users & roles, usage/quota today (Groq tokens, audio seconds), settings (limits, models, maintenance mode), audit log, failed evaluations (retry) |

### 4.4 Dialogs, states, and feedback

- **Dialogs:** confirm "End test early?", confirm delete question, confirm role change, mic permission help (browser-specific instructions).
- **Loading:** skeletons for lists/cards, step loader for evaluation, button spinners for actions. Never a blank screen.
- **Empty states:** "No tests yet — start your first Part 1 practice" with CTA.
- **Errors:** inline field errors (forms), toast for action failures, full-page `error.tsx` per route group with "Try again", custom `not-found.tsx`.
- **Navigation:** public top nav; app sidebar on desktop, bottom tab bar on mobile; admin sidebar with grouped sections; breadcrumbs in admin.
- **Leaving mid-test:** `beforeunload` warning; session can be resumed or marked abandoned.

### 4.5 Responsive and accessible

- Mobile-first; test at 360px, 768px, 1024px, 1440px.
- Exam room fully usable on phone (big record/finish buttons, cue card collapsible).
- Keyboard navigation everywhere, visible focus rings, `aria-live` for examiner captions and timer announcements, respects `prefers-reduced-motion`.

### 4.6 Images and assets

- **Static assets** (logo, illustrations, OG image, favicon): `/public`, SVG preferred, served by Vercel CDN, optimized via `next/image`.
- **Generated audio** (examiner scripts, question audio): **Vercel Blob**, public URLs with long cache headers.
- **Student audio:** **not stored permanently** in MVP (privacy + storage savings). Only transcripts and metrics are saved. Optional "keep my recordings" can come later.
- **User avatars:** come from Clerk (no storage needed).

### 5.2 Database schema (Drizzle)

| Table | Key columns | Indexes |
|---|---|---|
| `users` | id, clerk_id (unique), email, name, role, target_band, exam_mode_default, created_at, deleted_at | unique(clerk_id), index(role) |
| `topics` | id, name, part (1/2/3), category, is_active | index(part, is_active) |
| `questions` | id, part, topic_id, text, cue_card_points (jsonb, Part 2), rounding_off (Part 2), linked_cue_card_id (Part 3), difficulty, source, status (draft/published/archived), audio_url, audio_text_hash, created_by, timestamps | index(part, status), index(topic_id), index(linked_cue_card_id) |
| `examiner_scripts` | id, key (e.g. `welcome`, `part2_intro`), text, audio_url, audio_text_hash, version | unique(key) |
| `test_sessions` | id, user_id, mode, practice_mode, status (in_progress/completed/pending_evaluation/evaluating/evaluated/failed/abandoned), question_snapshot (jsonb), started_at, completed_at | index(user_id, created_at desc), index(status) |
| `responses` | id, session_id, question_id, part, order_index, transcript, transcript_status, duration_sec, word_count, metrics (jsonb: wpm, pauses, confidence) | index(session_id, order_index) |
| `evaluations` | id, session_id (unique), fc, lr, gra, pron, overall, feedback (jsonb), model, prompt_version, status, error, tokens_used, created_at | unique(session_id) |
| `api_usage` | id, user_id, kind (llm/stt/tts), model, tokens, audio_seconds, day, created_at | index(day, kind), index(user_id, day) |
| `app_settings` | key, value (jsonb), updated_by | pk(key) |
| `audit_logs` | id, actor_id, action, entity, entity_id, diff (jsonb), created_at | index(created_at desc) |

`audio_text_hash` = hash of the text used to generate audio. If the text changes, the audio is regenerated; if not, it is reused (zero repeat TTS calls).

### 5.3 Performance practices

- **Server Components by default.** Only the exam room, forms, charts, and interactive tables are client components.
- **Lazy loading:** exam room, Recharts, and admin tables load with `next/dynamic`.
- **Static / cached pages:** marketing pages are static. Published question lists are cached and invalidated by tag when admins edit (`revalidateTag`).
- **Database:** Neon serverless HTTP driver (fast cold starts), select only needed columns, indexes above, **cursor pagination** for history and admin tables, no N+1 (use joins / `with` relations).
- **Audio:** Opus/WebM at ~24–32 kbps mono → a 2-minute answer ≈ 0.5 MB (well under Vercel's 4.5 MB request body limit). Safari fallback: `audio/mp4`.
- **Parallel work:** transcription of answer *n* runs while question *n+1* plays, so results are ready almost instantly when the test ends.
- **Small bundle:** no heavy UI kits beyond shadcn; check with `@next/bundle-analyzer`.

### 5.4 Security practices

- Every route handler and server action: check auth → check role → validate input with zod → check ownership (a student can only access their own sessions — prevents IDOR).
- Secrets only on the server; only `NEXT_PUBLIC_*` keys reach the browser (Clerk publishable key only).
- Audio upload: check MIME type, max size (5 MB), max duration.
- Security headers in `next.config.ts`: CSP, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy: microphone=(self)`.
- Drizzle parameterized queries (no raw string SQL).
- Admin actions written to `audit_logs`.
- Privacy page + consent note before first test (audio is sent to Groq for transcription). "Delete my data" removes sessions, responses, evaluations.

### Stage 0 — Project Setup and Tooling

**What & why:** A clean, working foundation with CI and a live deploy from day one, so every later stage is shipped and tested continuously.

**Frontend tasks**
- `create-next-app` with TypeScript, Tailwind, ESLint, App Router, `src/` dir.
- Install shadcn/ui, set base theme tokens, fonts, `next-themes`.
- Simple placeholder home page.

**Backend tasks**
- `src/lib/env.ts` with env validation.
- `/api/health` route returning `{ ok: true, db: "up" }`.

**Database / integrations**
- `docker-compose.yml` with Postgres 16 for local dev.
- Drizzle config + DB client; Neon project created (main branch).
- GitHub repo, Vercel project connected, env vars set in Vercel.
- Prettier, Husky + lint-staged, Vitest, Playwright installed.
- GitHub Actions: typecheck → lint → unit tests → build.

**Completion criteria**
- `pnpm dev` runs locally against Docker Postgres.

## 8. Cost Optimization

### 8.1 Free-tier summary

> ⚠️ Limits change often. Numbers below are **approximate as of writing** — verify each one on the provider's pricing/limits page when signing up, and re-check before launch.

| Service | Free tier (approx.) | Main limitation | Our mitigation |
|---|---|---|---|
| **Vercel Hobby** | 100 GB bandwidth/mo, generous function invocations, `*.vercel.app` domain | **Non-commercial use only**; function duration limits; 4.5 MB request body | Keep payloads small; if you ever charge money, Vercel Pro ($20/mo) is required |
| **Neon Free** | ~0.5 GB storage per project, limited compute hours/month, scales to zero | Cold start (~0.5–1s) after idle; storage cap | Store transcripts not audio; small jsonb; archive old data |
| **Clerk Free** | ≥10,000 monthly active users | Some features (custom roles UI, removing branding) are paid | Roles via `publicMetadata` (free) |
| **Groq Free** | Per-model limits: requests/min, requests/day, tokens/min, tokens/day; Whisper also limits **audio seconds/hour and /day** | **Limits are per organization, shared by ALL users of the app** | See 8.2 |
| **Groq TTS** | Available on free tier with low limits | Low daily quota | Pre-generate once + cache; browser TTS fallback |
| **Vercel Blob** | ~1 GB storage, limited operations/transfer on Hobby | Small | Only examiner/question audio (~30 KB each); no student audio |
| **Upstash Redis** | ~500K commands/month | Command count | Only rate-limit checks use it |
| **Sentry Developer** | ~5K errors/month, 1 user | Event cap | Sample client errors, ignore noise |
| **GitHub** | Unlimited public repos; Actions free for public repos, ~2,000 min/mo for private | CI minutes (private) | Cache pnpm & Playwright; run WebKit E2E only before release |

### 8.2 Groq capacity reality check

Rough usage of **one full test**:
- STT: ~20 answers, ~7–9 minutes of student speech ≈ 450–550 audio seconds (Whisper may bill a minimum of ~10s per request).
- LLM evaluation: ~6K–10K tokens (rubric + transcripts + JSON output).

With typical free limits (e.g. ~28,800 audio seconds/day for Whisper and ~100K–500K tokens/day depending on model), the **LLM token budget is the bottleneck**: roughly **10–50 full evaluations per day** on the free tier, depending on the model. That is fine for development, beta testers, and early users — not for a large audience.

**How we stay inside the limits:**
1. **No runtime TTS** — all examiner audio is pre-generated and cached (≈0 TTS calls per test).
2. **No LLM for the examiner** — scripts are static; LLM is used once per test for evaluation.
3. **Compact prompts** — paraphrased short band descriptors; metrics instead of raw Whisper JSON; no duplicated instructions.
4. **Model fallback chain** — Groq limits are per model, so if the primary model's daily quota is used up, the next model is tried (each has its own quota).
5. **Per-user daily limit** (default 3 full tests or 8 single-part tests/day, adjustable by superadmin).
6. **Global budget guard** — when ~90% of the day's estimated quota is used, new tests show "Daily practice capacity reached, please come back tomorrow" instead of failing mid-test. A test that has started is always allowed to finish recording.
7. **Pending evaluations** — if evaluation is rate-limited, the session is saved and evaluated later (student retries via "Check again" or superadmin bulk retry).
8. **Minimum answer length** — skip STT for silent/near-empty recordings.
9. **Usage logging** — every call logs tokens/audio seconds in `api_usage`; superadmin dashboard shows today's usage vs limits.

**When you outgrow the free tier:** Groq's pay-as-you-go tier costs a few cents per full test at current pricing (verify). This is the cheapest upgrade path; nothing else in the architecture needs to change.

### 8.3 Other zero-cost choices

- Free `bandly.vercel.app` domain (custom domain is optional, ~$10/yr).
- Clerk handles all auth emails (no email service needed for MVP).
- Fonts self-hosted via `next/font` (no external font requests at runtime).
- Docker only for local Postgres — no paid container hosting.

## 9. GitHub, CI/CD, and Production

### 9.1 Branching and commits

- `main` = production (protected: PR required, CI must pass, no force push).
- Short-lived branches: `feat/exam-part1`, `fix/stt-safari`, `chore/deps`.
- One PR per small task; **squash merge** for a clean history.
- **Conventional Commits:** `feat:`, `fix:`, `chore:`, `test:`, `docs:`, `refactor:`.
- Tag releases: `v0.x` during development, `v1.0.0` at launch.

### 9.2 CI pipeline (GitHub Actions — `.github/workflows/ci.yml`)

On every PR and push to `main`:

1. Checkout → setup pnpm + Node (with cache)
2. `pnpm install --frozen-lockfile`
3. `pnpm typecheck`
4. `pnpm lint`
5. `pnpm test` (unit + integration, Postgres service container, `AI_MOCK=true`)
6. `pnpm build`
7. `pnpm test:e2e` (Playwright Chromium against the built app)
8. Upload Playwright report on failure

Dependabot enabled for weekly dependency PRs.

### 9.3 CD with Vercel

- Vercel Git integration: every PR → **Preview deployment**; merge to `main` → **Production deployment**.
- Preview deployments use a **Neon dev branch** database and Clerk development keys — never production data.
- **Migrations:** generated with `drizzle-kit generate`, committed to Git, applied with `drizzle-kit migrate` as part of the production build step (or a manual step at first). Rule: migrations must be **backward-compatible** (add columns first, remove later) so rollbacks are safe.

### 9.4 Environment variables and secrets

| Variable | Where |
|---|---|
| `DATABASE_URL` | Server only (local: Docker; preview: Neon dev branch; prod: Neon main) |
| `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | Server / public |
| `GROQ_API_KEY` | Server only |
| `BLOB_READ_WRITE_TOKEN` | Server only |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | Server only |
| `SENTRY_DSN` / `NEXT_PUBLIC_SENTRY_DSN` | Server / public |
| `SUPERADMIN_EMAILS` | Server only |
| `AI_MOCK` | Test/CI only |

- `.env.example` committed (no values); `.env.local` git-ignored.
- Secrets stored in Vercel project settings (per environment) and GitHub Actions secrets (only what CI needs — ideally none, because CI uses mocks).
- Env validated at build time by `src/lib/env.ts`.
- If a key leaks: rotate immediately in the provider dashboard, update Vercel, redeploy.

### 9.7 Monitoring

- **App:** Vercel "Instant Rollback" / promote a previous deployment (takes seconds).

- **AI changes:** prompt version and model are config — revert by changing `app_settings` or reverting the commit, no data migration needed.
